## Question

Should conversations be a first-class entity in the data model, or remain an arbitrary string grouping key on messages?

## Decision

Add a `conversations` MongoDB collection with `{id, tenantId, name}`. Conversations are seeded per tenant (not CRUD'd) and function as public channels within a tenant organization — accessible by any user in the tenant.

Keep `tenantId` denormalized on messages to preserve the existing compound index `{tenantId, conversationId, timestamp}` (DEC-001). Message creation validates that the target conversation exists and belongs to the authenticated user's tenant.

A new `GET /api/conversations` endpoint returns conversations for the authenticated tenant.

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Keep conversationId as arbitrary string | No schema change | No conversation listing, no ownership validation, weak domain model |
| Conversations entity, remove tenantId from messages | Cleaner normalization | Breaks ES search (needs joins), Kafka consumer needs enrichment, breaks DEC-001 index |
| **Conversations entity, keep tenantId on messages** | Strong domain model, conversation listing, preserves all existing indexes and queries | Minor denormalization (tenantId on both conversation and message) |

## Rationale

Conversations as a first-class entity enables a conversation list UI and validates that messages belong to a real, tenant-owned conversation. Keeping tenantId on messages avoids breaking the existing compound index strategy and Elasticsearch queries. The denormalization cost is minimal — tenantId is set once at creation and never changes.

## Invalidation Trigger

If conversation CRUD (create, rename, archive, delete) becomes a requirement, this decision should be extended with a full conversation lifecycle.
