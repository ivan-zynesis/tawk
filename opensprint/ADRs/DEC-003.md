## Question

How does the API authenticate requests and resolve tenant identity?

## Decision

- JWT bearer tokens containing `userId` (sub claim)
- A `user_tenants` MongoDB collection maps userId to tenantId
- `AuthGuard` validates the JWT; `TenantGuard` resolves tenantId from the authenticated user
- A `@CurrentTenant()` decorator injects the resolved tenantId into controller methods
- User signup, invitation, and tenant management APIs are out of scope — use test fixtures for development

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| tenantId in JWT claims | No DB lookup needed | Stale if user changes tenant, requires token refresh |
| API key per tenant | Simple | No user-level identity |
| **JWT userId + DB lookup** | Accurate, user-level auth | Extra DB read per request (cacheable) |

## Rationale

User-tenant association via DB gives us accurate tenant resolution and supports future multi-tenant users. The lookup is cacheable. Out-of-scope APIs are replaced by seed fixtures.

## Invalidation Trigger

None. We believe this should be the right choice for a multi-tenant system use case. However, this consideration will be irrelevant for single-tenant setup.
