## Question

How do we provision infrastructure for integration tests?

## Decision

Use testcontainers to orchestrate MongoDB, Kafka, and Elasticsearch containers per test suite. A centralized `TestSetup` class manages container lifecycle and bootstraps a fully wired NestJS test app with overridden connection URIs. Tests are self-contained — no external `docker compose up` required.

- `TestSetup.create()` starts all three containers, bootstraps the NestJS app, and returns the app instance + JWT helper
- Containers are started once per test suite (`beforeAll`), torn down in `afterAll`
- Test isolation via unique data values (conversationId, tenantId) per test, not database cleanup

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Docker Compose (CI-provisioned) | Same config as dev, simple test code | Tests can't run standalone, requires `docker compose up` first |
| In-memory fakes (mongodb-memory-server etc.) | Fast, no Docker needed | Doesn't test real Kafka/ES behavior, fake divergence risk |
| **Testcontainers** | Self-contained, portable, tests real infra | Container startup time (~15-30s), requires Docker daemon |

## Rationale

Testcontainers give us real infrastructure without external dependencies. The centralized TestSetup layer prevents testcontainer boilerplate from spreading across every test file. Container startup cost is amortized by running once per suite.

## Invalidation Trigger

If container startup time becomes prohibitive for CI feedback loops, consider hybrid approach (testcontainers for pipeline tests, mocks for fast feedback).
