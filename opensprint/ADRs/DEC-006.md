## Question

What test runner and TypeScript transform do we use for unit and integration tests?

## Decision

Vitest as the test runner with unplugin-swc (SWC) as the TypeScript transform. A single `vitest.config.ts` configures both unit and integration test projects via workspace projects.

- Vitest runs natively in ESM — resolves `.js` extension imports required by `nodenext` moduleResolution without hacks
- SWC handles NestJS `emitDecoratorMetadata` + `experimentalDecorators` (esbuild, Vitest's default, does not)
- `globals: true` provides `describe`/`it`/`expect`/`vi` without explicit imports
- Workspace projects separate unit (`src/**/*.spec.ts`) and integration (`test/integration/**/*.integration.spec.ts`) with independent timeout and pool settings

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Jest + ts-jest | Mature ecosystem, NestJS default | CJS/ESM mismatch with `nodenext` moduleResolution; `.js` imports fail; requires `moduleNameMapper` hack and separate `tsconfig.spec.json` |
| Jest + tsconfig.spec.json | Fixes module resolution | Band-aid — two tsconfigs diverge, IDE and test runner see different type worlds |
| **Vitest + SWC** | Native ESM, single config, fast transforms, `.js` imports work out of the box | Requires SWC plugin for decorator metadata; Vitest 4 requires Node >= 20.19 |

## Rationale

The project uses TypeScript `nodenext` moduleResolution which mandates `.js` extensions on imports. Jest + ts-jest runs in CommonJS and cannot resolve these extensions without fragile workarounds that break IDE test runners. Vitest eliminates this impedance mismatch entirely by running in ESM natively. SWC is required because NestJS relies on `emitDecoratorMetadata` which esbuild does not support.

## Invalidation Trigger

If NestJS drops the `emitDecoratorMetadata` requirement (unlikely in current major version), the SWC plugin could be replaced with Vitest's default esbuild transform.
