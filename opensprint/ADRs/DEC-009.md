## Question

How do we enable independent scaling of the HTTP API and Kafka consumer when they have different scaling profiles?

## Decision

Introduce an `APP_MODE` environment variable with three modes:

- **`monolith`** (default) — loads all modules, current behavior. Used for local development and tests.
- **`api`** — HTTP-facing modules (Auth, Messages, Conversations, Health, Seed) with Kafka producer. Bootstraps via `NestFactory.create()` with HTTP listener. Handles all REST endpoints including message creation and Kafka event publishing.
- **`worker`** — Kafka consumer modules only (Search with Kafka consumer + ES indexer, Seed). Bootstraps via `NestFactory.createApplicationContext()` — no HTTP listener. Consumes events from Kafka and indexes into Elasticsearch.

Single entry point `main.ts` reads `APP_MODE` and conditionally bootstraps the appropriate module. Same Docker image, different env var per deployment.

### Scaling profiles

| Mode | Scales with | HTTP | Kafka Producer | Kafka Consumer |
|---|---|---|---|---|
| `monolith` | Everything | Yes | Yes | Yes |
| `api` | HTTP traffic (reads + writes) | Yes | Yes | No |
| `worker` | Kafka partition count / consumer lag | No | No | Yes |

### Deployment example

```
                    ┌──────────────┐
  Load Balancer ────│   api × N    │  ← scales with HTTP traffic
                    └──────┬───────┘
                           │ Kafka [message-created]
                    ┌──────┴───────┐
                    │  worker × M  │  ← scales with partition count
                    └──────────────┘
                           │
                    Elasticsearch [messages]
```

### Not in scope

Kafka broker scaling (partition count, broker instances, compute allocation) is an infrastructure concern managed at the ops layer (Terraform, Helm, docker-compose config), not in application code.

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Run multiple monolith instances | Zero code changes, Kafka auto-rebalances | Scales HTTP and consumer together, wastes compute if only one side needs scaling |
| Separate packages (monorepo) | Strongest separation | Overkill for shared codebase, duplicates build/deploy |
| **APP_MODE flag (api + worker)** | Independent scaling per concern, one codebase, backward compatible | Minor conditional logic in main.ts |

## Rationale

The application has two independent scaling axes: HTTP traffic (API requests) and indexing throughput (Kafka consume + ES index). The API includes both reads and writes with Kafka producing — these scale together since write requests are what drive Kafka events. The worker scales independently based on consumer lag and partition count. Kafka broker infrastructure (partition count, replication, compute) is managed separately at the ops layer and is not an application concern.

## Invalidation Trigger

If the worker accumulates its own unique dependencies not shared with the API (e.g., ML models, heavy compute libraries), extract it into a separate package.
