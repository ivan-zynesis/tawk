## Question

How do we isolate tenant data across MongoDB and Elasticsearch?

## Decision

Shared infrastructure with tenantId-based filtering:
- Single MongoDB collection `messages` with compound index `{tenantId, conversationId, timestamp}`
- Single Elasticsearch index `messages` with tenantId as a keyword filter field
- All queries must include tenantId — enforced at the service layer

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| Database-per-tenant | Strongest isolation | High operational overhead, complex provisioning |
| Collection-per-tenant | Moderate isolation | Index management per tenant, schema migrations multiply |
| **Shared + tenantId filter** | Simple ops, uniform schema, single set of indexes | Noisy neighbor risk at extreme scale |

## Rationale

At current scale expectations, shared infrastructure is operationally simplest. Compound indexes ensure query performance. Tenant isolation is enforced at the application layer via guards.

## Invalidation Trigger

If tenant count exceeds thousands or regulatory requirements demand physical data isolation.
